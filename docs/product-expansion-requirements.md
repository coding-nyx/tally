# Tally accounts, statements and agent workflows

Status: **requirements and proposed implementation**, 13 October 2026. Repository baseline: `f3e9cbd21bff430670c09858a0e9fe97d117caac`. The original gap mapping below is frozen at that baseline. The subsequently authorized first account/database foundation is now implemented and deployed; current scope and verification limits are recorded in [accounting-foundation.md](accounting-foundation.md). Phase B now has a bounded deployed implementation with remaining verification; see [statement-foundation.md](statement-foundation.md). Phases C–E remain proposed.

## Product goal and change authority

Tally will be a self-hosted financial workspace used through the website, a built-in agent, and external Codex/Hermes/other MCP clients. Scheduled follow-ups request missing bank/card statements. The user uploads selected statements; an agent prepares account-aware, traceable changes for owner review. The website shows recorded account balances, cash, liabilities, spending and money movement, with historical analysis and explicit coverage/freshness limits.

This scope expands the current monthly budget planner. Preserve existing code, browser-local material, independent INR/USD ledgers, reviewed operations, receipts and audit history. Planning/documentation is authorized. **Each specific commit, tag, push, merge, deployment, credential operation or live financial-data change needs explicit approval.** No AI attribution lines in commits or PRs. Mac Tally servers must remain stopped until the user requests otherwise. No provider calls, live-data upload or access-policy changes are authorized by this plan. Preserve private hub `/finance/`, Caddy/Tailscale and unrelated service routing.

Subsequent user confirmation authorized token-free unrestricted access for clients permitted through the existing private Tailscale route. The requested implementation keeps validation/revisions/idempotency and review steps, but a shared principal cannot enforce separate human-vs-agent identities or exclusive owner approval. See [the authentication assessment and implementation status](tailscale-auth-proposal.md). R8/R9 below record the expanded product's original separate-actor requirements; those stronger identity guarantees are not provided by the selected unrestricted mode and would require a later explicit policy change.

## Required behavior and accounting invariants

1. **Accounts (R1):** bank, cash wallet, credit card and loan/liability accounts, stable ids, individual currency, display label, institution/optional masked identifier, lifecycle and opening date. Owner-review opening amounts and cutoffs; allow unknown openings as unknown. Archive instead of erasing financial history. Show recorded balance as of a date and reconciliation status.
2. **Journal (R2):** use positive integer minor units with explicit debit/credit sides. Each posted journal balances by currency; one event may have multiple postings and category allocations. INR/USD remain independent initially; reject implicit cross-currency transfers. Future consolidated valuation needs explicit dated FX source/rate/rounding and valuation date, separately from native balances.
3. **Sources/matching (R3):** immutable source bytes/digest, statement/row/page references, provider reference and parsed observations link to canonical events. One event can have multiple statement observations. Unmatched or ambiguous counterparts stay visible. Similar date/amount/merchant alone never proves duplication. Reviewed decisions preserve repeated legitimate purchases.
4. **Inbox/reconciliation (R4):** store account, period, opening/closing balances and parser version. Workflow: stage → extract/map → match/classify → preview account/category/debt changes → owner approval → atomic commit → reconcile. Preserve row errors, confidence reasons, uncertain suggestions, gaps/overlaps and discrepancy resolutions. No invented entries or forced balance. Supported CSV/text PDFs first; bank parsers follow deliberately selected fixtures. OCR/encrypted/scanned support is a separately designed feature, never a silent AI fallback.
5. **Debt/cash (R5):** card recorded outstanding is distinct from statement amount due, remaining due/minimum, statement date, payment date and limit. Loans expose principal, interest/fees and settlement breakdown; borrowing is not income. Cash requires owner-supplied opening count and manual cash activity. Cash adjustments need an explicit observed count, reason and approved correction.
6. **Classification (R6):** category groups and income/expense categories remain independent of accounts. Merchant aliases and user-approved versioned rules suggest allocations. Preserve manual overrides unless explicitly replaced. Allocations must equal the event's expense/income component; unresolved classifications enter a queue.
7. **Website (R7):** account balances, cash, card/loan liabilities, dues, recorded net position with tracked scope, income/expense and cash movement, category/group/merchant/account breakdowns, budgets/goals and history. Every balance/report exposes period/as-of, account scope, currency, opening-known flag, latest source/coverage, reconciliation state and missing/stale evidence. Statement closing balance is an observation at its date, not live bank connectivity.
8. **Agent parity (R8):** same domain contract for website, built-in agent and external MCP. Actor identity, account/currency/operation grants, validation, revision, approval and audit rules apply equally. Built-in agents cannot inherit the human approval role or self-approve. No agent writes SQL or bypasses service checks.
9. **Hosted clients (R9):** HTTPS Streamable HTTP alongside existing stdio, discovery, per-agent revocation/expiry/rotation/account grants, selected OAuth or unattended identity flow. Private Tailscale identity is an optional access design pending the separate decision. Network reachability never substitutes silently for owner review. Test actual Codex and Hermes, not only SDK mocks.
10. **Follow-ups (R10):** persistent per-account weekly/monthly statement schedule, IANA user timezone, expected period and grace interval; missing statement, unresolved review and due-date conditions; chosen channel, quiet hours, snooze, deduplication, resolution suppression, history/retries. Select exactly one delivery owner (Tally or Hermes); reminder generation is deterministic and does not need an LLM. Recurring preference is not authorization to send messages or activate a scheduler now.
11. **Analysis (R11):** deterministic totals from posted records first. AI can interpret authorized dated reports with source links/freshness; it cannot invent authoritative balances or do final arithmetic. Report filters/provider/minimized payload/exact question form an approval-bound context. New row/merchant disclosure requires explicit consent beyond existing aggregate-only approval.
12. **Migration/operations (R12):** retain original local/server exports and current ids/history; explicitly review legacy account assignment and opening cutoffs. Persistent DB/files/jobs/secrets and encrypted off-device backups with verified restore. Posted corrections use reversals/compensating events; never silently rewrite reconciled history. Drafts can be cancelled without posting; cancellation after commit does not undo postings.

### Proposed posting rules

Public bank/cash/card/loan accounts map to ledger accounts. Internal income, expense, opening-equity and clearing accounts balance journals but are not displayed as bank funds. Normal balance: assets/expenses debit; liabilities/income/equity credit. Report expenses net of linked refunds, with gross/refund views available. Cash flow derives from asset postings, not journal count.

| Event               | Debit                                 | Credit                      | Income/expense effect                       |
| ------------------- | ------------------------------------- | --------------------------- | ------------------------------------------- |
| Salary received     | Bank                                  | Income, category Pay        | Income once                                 |
| Bank/cash purchase  | Expense/category allocations          | Paying asset                | Expense once                                |
| Card purchase       | Expense/category allocations          | Card liability              | Expense once; debt increases                |
| Card payment        | Card liability                        | Bank/cash                   | No extra expense                            |
| Own-bank transfer   | Destination bank                      | Source bank                 | Neither income nor expense                  |
| ATM withdrawal      | Cash wallet                           | Bank                        | Neither; fee is separate expense if present |
| Loan drawdown       | Bank/cash                             | Loan liability              | Not income                                  |
| Loan repayment      | Loan principal + interest/fee expense | Paying asset                | Principal not spending; interest/fees are   |
| Purchase refund     | Receiving asset or card liability     | Original expense allocation | Reduces expense; references original event  |
| Opening asset/debt  | Asset or opening equity               | Opening equity or liability | No period income/expense                    |
| Reversal/correction | Exact compensating postings           | Exact compensating postings | Linked dated correction; preserve original  |

Amounts must sum exactly for split postings; reject overflow and fractional minor units. Account types, currencies, archive dates and posting dates must agree. A credit-balance card overpayment remains signed credit owed to the user, not a clamped zero liability. Do not net unrelated accounts silently.

When the destination of a movement is known and reviewed, book both accounts once and mark the missing statement observation as awaiting evidence. If the counterpart is unknown, retain a draft/unmatched observation by default. An explicitly approved unresolved-clearing event may represent that known source row, with visible unresolved scope; it cannot be generated from a reconciliation difference or represented as known income/expense. Later matching changes source links or makes a reviewed compensating correction rather than duplicating the movement.

All financial foreign keys enforce workspace ownership and account currency. Use SQL `BIGINT` with a deliberate API safe-integer bound and checked aggregates; continue integer-minor JSON amounts within that bound. Do not silently coerce PostgreSQL bigint strings to imprecise JS numbers. Journal balance validation and receipt/audit creation run in the same transaction; lock the workspace revision initially and use stable lock ordering if per-account concurrency is introduced. Posted rows become immutable through runtime permissions/service constraints; corrections create linked events.

Observation identity uses provider transaction/reference id plus account/institution when reliable, or exact file/statement-row identity for upload replay. File hash deduplication does not collapse separate legitimate row occurrences. Provider-id reuse or conflicting observations creates review items. Date/amount/merchant fingerprints create candidates only. Preserve separate original booking dates when linked statements book the same event on different days; explain any chosen canonical/reporting date.

Private source files should use protected persistent blob storage outside the web root, scoped to workspace with hashes/encryption/retention and authenticated download. File writes cannot join a SQL transaction: stage bytes first, verify their hash, commit an immutable reference with the financial transaction, and clean up unreferenced staged blobs via durable jobs. Database and referenced blob versions must be restorable together.

## Migration and operations

1. Export untouched INR/USD browser-local backups from each chosen authoritative browser and any existing shared workspace; record hashes, ids/counts and origin. Do not auto-read localStorage or infer that all browsers hold the same ledger. No live export/import is performed by this plan.
2. Add normalized schema/storage behind an off-by-default feature flag. Preserve current JSONB documents and backups. Build an isolated synthetic restore and dry-run migration before activation.
3. Stage legacy entries into `legacy_entries` with currency/category/settings/history intact. Dates/kind/amount alone cannot determine bank/card/cash. Keep unassigned entries visible in a separate legacy reporting view; exclude them from authoritative account positions until reviewed mapping.
4. Owner selects per-account cutoffs and whether an opening is before the day's movements or the close-of-day observation. Transactions already included in a closing opening balance remain historical evidence and are not posted again to that opening's future account timeline. Older legacy reporting, pre-cutoff evidence and post-cutoff postings must not be added together twice. No inferred opening from income-minus-expense.
5. Preview mapping of accounts, transaction kinds, categories, repayments/transfers/splits and duplicates. Legacy card payments originally marked expense need explicit reclassification/reconciliation against purchases; never automatically re-label based on descriptions. Preserve manual mappings and uncertainty. Review opening equity/cutoffs and per-account balance effects.
6. Freeze/approve migration batch. Commit journals, source/migration mappings, settings, receipts and audit atomically with unique source ids. Re-run/restart must replay exactly; block concurrent legacy writes during approved cutover. Avoid permanent dual writes across two models.
7. Compare income/expense results and account position against the approved conversion preview and statement closings. Differences remain review items. Test encrypted off-device backup + restore of DB/files/jobs/identity configuration on an isolated target.
8. Only after specific activation approval designate the normalized workspace authoritative. Preserve old mode/export and migration receipts. Before first live postings, rollback can discard the unused new store; afterward rollback needs backup/controlled correction or roll-forward, not blindly selecting an older image that cannot read new schema.

For hub, choose durable storage before finance depends on it. Assess durable storage and power-loss recovery separately before production use. Protect secrets and source blobs, expose no DB host port, apply deliberate migrations with a separate admin role, and keep backup/restore/runbooks and restart health. The Node self-hosted target needs a durable worker; the default Vercel build cannot supply local persistent files or an always-running scheduler. Provider configuration remains off until chosen and privately set up.

### Synthetic end-to-end acceptance fixture

Two INR banks A/B, one card, one loan and cash; USD stays unchanged. All values below are **minor units**, not real financial data. Reviewed openings: A=100000, B=20000, cash=5000, card debt=10000, loan principal=50000; opening recorded net position=65000.

Post salary 60000 to A; three card purchases (3000 and two legitimate 500 purchases sharing date/merchant but distinct references); card payment 4000 from A; transfer 10000 A→B; ATM movement 2000 A→cash; loan payment 6000 from A split principal 5000/interest 1000; borrowing 8000 into A; cash purchase 500; linked card refund 500. Import overlapping/repeated fixtures with both bank/card repayment observations and both transfer observations; then import the missing counterparts later. No event is duplicated and no legitimate repeated purchase is discarded.

Expected final recorded amounts: **A=146000, B=30000, cash=6500, card liability=9500, loan principal=53000; assets=182500, liabilities=62500, net position=120000; income=60000, net expense=5000.** Transfers, ATM, borrowing, card principal payment and loan principal never become extra income/expense. Show original card statement due separately from newer recorded outstanding.

Additional required checks:

- Closing observations agree with computed balance or show the exact unresolved difference; absent statements/openings are marked missing/unknown. An intentionally wrong close cannot produce a balancing journal.
- Invalid date/currency/account or uncertain split/match blocks commit until reviewed correction/exclusion. Correcting source rows invalidates old previews/approvals. Manual classification survives rule re-runs.
- Owner approves every frozen import/opening/correction requiring review; built-in/external actors cannot approve their own plans. Authentication-mode changes do not silently alter this gate.
- Interrupt response after DB commit, retry with identical key/args, restart app/DB/worker and replay: one event, one receipt, original result. Stale revisions and key reuse with changed arguments fail without partial data.
- Missing one expected account statement creates one follow-up after grace/quiet hours; repeated workers/restarts do not duplicate it; uploading/reconciling it suppresses unsent follow-ups. Existing delivery attempts remain traceable.
- UI, built-in agent, stdio and hosted MCP yield equivalent postings/reports and source links under equivalent grants. Every report exposes tracked scope/as-of/coverage, and historic results include correction history.
- Back up DB and referenced blobs, restore an isolated copy, recompute the same journal/account/report results and retained audit/source references. No real provider calls are needed for these fixtures.
